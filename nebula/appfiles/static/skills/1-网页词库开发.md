【网页词库开发（WebNebula / .wn）】
目标：编写 / 修改 .wn 网页词库，让网页被访问时由脚本生成内容。写执行块前先读取「词库语法结构」技能——.wn 的执行块与 .n 共用同一套 Nebula 语法。

一、文件与位置
1. .wn 是「HTML 容器 + 内嵌执行块」的网页词库，UTF-8 编码，默认放在网站根目录（public/）下，访问路径即文件路径：public/index.wn ↔ /index.wn（默认首页），public/404.wn ↔ /404.wn（页面不存在时的兜底页）；
2. 请求由 system/router.n 路由：.wn 分支先 $设置头部 Content-Type text/html;charset=UTF-8$ 再 $执行网页词库文件 <路径>$；文件不存在时输出 404.wn。

二、执行模型（与机器人 .n 完全不同，最容易搞错）
1. .wn 没有触发词：文件里的执行块自动依次执行，不等待任何消息——不要写 Main，也不要用 %参数N%（那是消息匹配用的）；本智能体产出的文件一律是 .wn，禁止写成 .n，也禁止出现「触发词独占一行 + 正文」这种 .n 词条结构；
2. 执行块有两种写法，块内都写服务端 Nebula 语法，优先用第一种：
   ① <?n ... ?> 内联块（推荐）：就地执行，结果原样插回块所在的位置，所以可以写在 HTML 的任意位置（段落里、行内都行）；块内的裸文本会成为该处的页面内容，也可以直接输出 HTML 片段。写法固定为「<?n 单独占一行 + 块内每条语句各占一行 + ?> 收尾」（?> 后面可以直接跟同一行的 HTML 标签，如 ?></p>；块内按行解析，多条语句不要挤在同一行），标记本身不出现在最终页面里；
   ② <script type="nebula"> 脚本块（兼容写法，适合大段多行脚本）：只识别直接挂在 <head> / <body> 下的块（type 必须是 nebula；嵌套在其它标签内部的不会被识别）；写在文件末尾（</html> 之后）的脚本会被解析器并入 body，同样有效，参考 public/404.wn；块执行完即从页面中移除，不会出现在最终 HTML 里；
3. 两种块共用同一个变量作用域，块里赋的变量后面的块可以直接用（可以接力计算）；但实际执行分两轮：先把文件里所有 <?n ... ?> 内联块按出现顺序跑完，再按文档顺序跑所有 <script type="nebula"> 脚本块——所以「脚本块写在前、内联块写在后还能接力」是不成立的，需要接力就把上游写成内联块，或统一都用脚本块；块内可用完整 Nebula 语法（变量赋值、判断 / 循环框、[函数] 定义、内置函数与对象方法）；两种块可以混用在同一个文件里；
4. 需要输出「一段内容」时，内联块直接就地输出即可，不必绕道模板；需要把值放到页面别处、或要在普通 <script>（JS）里用时，才在块里赋值、页面用 {{.键}} 取；
5. 这两种块都是「服务端 Nebula 脚本」，不是 JavaScript：脚本块的名字虽然叫 script，但它由 Nebula 在服务端执行、执行完即被移除，浏览器看不到它，也拿不到它的内容。禁止在块里写 JavaScript（let / const / var / function / 箭头函数 / document / window / console / alert / fetch / setTimeout / addEventListener 等一律不行），也禁止用 document.write / console.log / 弹窗输出——写了不会报错，但只会被当成普通文本或被丢弃，不会执行，页面毫无效果（典型表现是白屏、或原样显示一行代码）。
6. 需要浏览器端 JavaScript（点击交互、canvas 绘制、动画、定时刷新）时，另外写一个不带 type 属性的普通 <script>（或 <script type="text/javascript">）：Nebula 不会执行这种块，会把它原样留在最终 HTML 里交给浏览器运行。两种块各写各的，不要混写，尤其不要用 <script type="nebula"> 或 <?n ... ?> 把 JS 包起来（那样 JS 完全不生效）；普通 <script> 里要用脚本产出的数据，同样写 {{.键}}（Go 模板会按 JS 上下文转义）。

三、输出与模板渲染
1. 所有执行块跑完后，整份 HTML 会用 Go html/template 渲染一次，把 {{.键}} 替换成脚本产出的数据；
2. 数据来源按块的写法区分：
   内联块 / 不带 id 的脚本块：块里赋值产生的变量并入模板数据，页面写 {{.变量名}}；内联块的裸文本本身已经就地输出，不需要再取一次；
   带 id 的脚本块：data[id] = 该脚本块的执行输出，模板里写 {{.id}}（如 <script type="nebula" id="发布号">发布号:1.0.0
%发布号%</script> → {{.发布号}} 得到 1.0.0）；
3. 只有「赋值」产生的变量才会进模板数据；块里的裸文本只是就地输出，不会变成模板键（脚本块的裸文本就是它的输出，只对带 id 的块有意义）；
4. 模板键写错不会报错、只会渲染成空——页面出现大片空白时，先核对变量名与 id 是否一致；
5. 别拿内置「魔术变量」当自己的变量名：版本、时间、时间戳、空格、换行、系统、昵称 等取值由运行环境内置提供，优先级高于你自己赋的值——写成 版本:1.0.0 再 %版本% 取到的仍是程序版本号，不是 1.0.0。自己的数据请另起名字（如 发布号、站点名）；
6. 模板数据只能是文本：{{.键}} 一律会被 HTML 转义后插进页面。二进制数据（如 $画布.获取$ 返回的 PNG/JPEG 字节）不能整串丢给模板——放进文本位会变成乱码，整串塞进 <img src="{{.键}}"> 又会被 Go html/template 的 URL 过滤器换成 #ZgotmplZ（过滤器只放行 http/https/mailto，带 data: 的整串会被拒）；
7. 但 .wn 里用画布产图是支持的（执行块在页面渲染前先跑完，相当于把图提前备好再交给页面）。把画布图片交给页面有两种写法：
   ① 模板里写 data: 字面前缀，变量只放 base64 正文：块里写 b64:$B64编码 %图2%$，HTML 里写 <img src="data:image/png;base64,{{.b64}}">（前缀必须是模板里的字面量，整串 data URI 放进变量就会被换成 #ZgotmplZ）；
   ② 落盘成静态文件：块里写 $写文件 public/out.png %图2%$，HTML 里写 <img src="/out.png">（按原始字节写入、不会被转义，注意会在网站目录留下文件）；
   只有赋值后既不进模板、也不写文件才是无意义的死代码。页面上纯前端绘制的图形仍可直接用 HTML/CSS 或浏览器原生 <canvas>（canvas 的 JS 必须写在普通 <script> 里，写进 type="nebula" 块或 <?n ?> 块都不会执行）。

四、完整示例
<!DOCTYPE html>
<html lang="zh-CN">
<head>
    <meta charset="UTF-8">
    <title>我的站点</title>
</head>
<body>
    <h1>你好，{{.昵称}}</h1>
    <p>版本信息：v <?n
发布号:1.0.0
%发布号%
?></p>
<?n
昵称:$GET 名字 访客$
?>
</body>
</html>
（<p> 里的内联块就地输出 1.0.0；文件末尾那个内联块赋值的「昵称」并入模板数据，页面用 {{.昵称}} 取到。示例里没用 {{.版本}}，因为「版本」是内置魔术变量，见「三」第 5 条。需要浏览器端交互 / 动画时另写一个普通 <script>（不带 type="nebula"），例如 <script>document.title = "v" + {{.发布号}};</script>——这种块 Nebula 不执行，浏览器才会执行它。多行脚本也可以写成 <script type="nebula"> 脚本块，效果相同，只是要挂在 head / body 下。）

五、HTTP 相关
1. .wn 被访问时可用 $GET key 默认值$ 读查询参数、$POST key 默认值$ 读表单 / JSON 参数、$全局变量 访问数据$ 取整个请求信息（路径 / 来源 / 请求头 / IP / Host / POST / POSTFile）；
2. 响应头用 $设置头部 key value$；响应状态用 $全局变量 响应状态 404$；额外头部用 $全局变量 输出头部 {"Location":"https://..."}$；
3. 不要用 $全局变量 输出类型$ 设内容类型（这条路径没有读取它），要改 Content-Type 就用 $设置头部 Content-Type ...$（router.n 已默认设为 text/html;charset=UTF-8）。

六、注意事项
1. .wn 不能承载机器人功能：机器人只执行 <账号路径>/dic/ 下的 .n，用户发消息不会触发 .wn；
2. 需要 JSON / 纯文本接口时改用被 HTTP 访问的 .n（以 Main 为触发词），不要用 .wn 硬凑，见「API词库开发」技能；
3. 内置函数与对象方法的准确用法一律以内置文档为准：先用 search_docs 检索（直接返回命中小节的原文），不够再 read_dic_doc 读整篇（语法规则见「词库语法结构」技能）；不确定就查证或向用户确认，不要往文件里塞试探代码；
4. 本智能体只负责 .wn：先看系统提示里「当前任务关联的词库文件」（用户此刻在编辑器打开的文件）——它已经是 .wn 就直接改它，不要另建新的 .wn；若它是机器人 .n 之类的非网页文件、且用户本次请求就是要改它，不要把它改写成网页词库，应先用 switch_agent 把任务交给负责该类型的智能体（「机器人词库」「API词库」等）并说明一句已转交给谁——切换立即生效，随后就按接手方的职责继续，不要停下等用户再发消息；判断依据是文件类型与落点目录，不是功能名称（「九宫格」这类功能名三种场景里都可能出现），不要仅凭它交接；用户本次请求与那个文件无关（只是让你实现一个功能），或没有对应智能体可交时，不交接，改在网站根目录 public/ 下新建 / 修改 .wn 文件；反过来，也绝不能把网页需求写成 .n（无触发词的 .n 根本不生效，用户发消息也不会触发）；
5. 改完必须验证：save_dic 保存 .wn 会返回执行块（<?n ?> 内联块 / <script type="nebula"> 脚本块）的变量检查与模板键核对的 warnings（「变量赋值后未被使用」= 死代码、「模板键不存在」= 页面渲染成空），有 warnings 必须逐条修掉再重新保存；保存后调用 run_web_dic 运行一次，检查返回的最终 HTML 里执行块已消失（脚本块整块没了、内联块只剩它输出的内容）、{{.键}} 已被真实数据替换；若渲染结果是空白或模板键没被替换，先核对 id / 变量名再重新保存与运行，不要凭「保存成功」就汇报完成。
6. 编辑器保存时会按 HTML 结构自动缩进：<?n ?> 内联块的正文会按 Nebula 块结构排版，两种块的行首缩进在解析前都会被自动裁掉，所以块内不必刻意顶格写；但块内确实要保留行首空白时（例如文本框内容本身带缩进），用 //@关闭缩进 与 //@启用缩进 把这几行夹起来，这对标记之间的行首空白会原样保留。
